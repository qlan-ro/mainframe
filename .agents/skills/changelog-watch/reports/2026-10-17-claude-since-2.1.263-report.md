## Compatibility risks

### high — Changed the task-tracking tools (TaskCreate/Get/Update/List, TodoWrite) to be offered only on Claude 3.x, Opus 4.0–4.7, Sonnet 4.0–4.6, Haiku 4.5; set `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` elsewhere (2.1.268)

- Checklist row: `CLAUDE-EVT-02` — `src/assistant_event.rs::handle_assistant_event` (TodoWrite and TaskCreate/TaskUpdate/TaskStop branches in `src/assistant_event_tools.rs::scan_tools`)
- Why it threatens the row: the 2.1.233 change used a denylist of new models. This one is an allowlist of old ones. Any model outside the list loses the tools, including every CLIProxy model (`cliproxy/`-namespaced ids such as GPT models routed through `CLAUDE-ENV-01`). The todo list and the task_v2 tracker stay empty, and nothing reports an error. A grep of `packages/core-rs/crates/` finds no `CLAUDE_CODE_ENABLE_TODO_TOOLS`, so the gap the earlier report flagged is still open. This entry confirms that risk and widens its reach.
- Recommended regression test: add `#[test] a_session_spawn_opts_into_the_todo_tools` in `src/session_tests_spawn_part_1.rs`, next to `a_native_session_carries_no_endpoint_env`. It should assert that the `build_spawn_command` env has `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` for both native and proxy sessions. `src/events_tests_notifications.rs::todo_write_fires_todo_update` passes either way because it feeds a synthetic event.
- Verify live: .claude/skills/claude-protocol-debugger/

### medium — Improved startup in `--input-format stream-json` sessions: the first turn no longer waits up to 2s for still-connecting MCP servers whose tools tool search defers; they arrive on a later turn (2.1.274)

- Checklist row: `CLAUDE-FLAG-04` — `src/orchestration_args.rs::orchestration_args`
- Why it threatens the row: Mainframe injects the `mainframe` HTTP server with `alwaysLoad` unset, so tool search defers its tools. Under 2.1.274 the first turn of a stream-json session no longer waits for the server to connect. A first prompt such as "delegate this to codex" can therefore run with no `mcp__mainframe__*` tools at all. The agent says it has no such tool, and the next turn works. The 2.1.274 `CLAUDE_CODE_MCP_STARTUP_WAIT_MS` entry, and `alwaysLoad` (see the no-action entries for 2.1.269 and 2.1.271), are the two possible mitigations.
- Recommended regression test: `src/orchestration_args_tests.rs::args_carry_the_placeholder_timeout_and_allow_rule_but_never_the_token` currently asserts `server.get("alwaysLoad").is_none()`. Once a live check confirms turn-one tools go missing, change it to pin the chosen mitigation: either `alwaysLoad: true` in the inline `--mcp-config` JSON, or extend `the_token_rides_in_the_child_env` to assert a `CLAUDE_CODE_MCP_STARTUP_WAIT_MS` value in the child env.
- Verify live: .claude/skills/claude-protocol-debugger/

### medium — Improved dynamic workflows to pause when you hit your usage limit and continue automatically when it resets, instead of dropping the affected agents (2.1.271)

- Checklist row: `CLAUDE-EVT-01` — `src/task_events.rs::handle_task_updated` (status mapping in `packages/core-rs/crates/mainframe-claude-workflows/src/status.rs::task_update_action`)
- Why it threatens the row: `task_update_action` treats `"paused"` as terminal (`End(Stopped)`), and `handle_task_updated` closes the background task when it sees it. Before this change a paused workflow stayed paused, so that was harmless. Now the same workflow resumes on its own. The task panel shows it stopped while it keeps running and later completes, and a later `"running"` maps to `Ignore`, which does not reopen the task. The workflow-run store maps `"paused"` to `Paused` and is fine. Only the background-task tracker is wrong.
- Recommended regression test: add `#[tokio::test(start_paused = true)] handle_task_updated_keeps_a_paused_workflow_open_until_it_resumes` in `src/task_events_tests_part_2.rs`. Feed a `local_workflow` task `task_updated` statuses `"paused"`, then `"running"`, then `"completed"`. Assert that the tracker still has the task open after `"paused"` and closes it as Completed only at the end.
- Verify live: .claude/skills/claude-protocol-debugger/

### medium — Improved prompt-cache stability: subagents and sessions started with `--system-prompt` or `--append-system-prompt` now record the system prompt and tool definitions once instead of re-rendering them (2.1.267)

- Checklist row: `CLAUDE-FLAG-01` — `src/session_spawn.rs::{build_args, append_system_prompt_text}`
- Why it threatens the row: Mainframe passes `--append-system-prompt` on every spawn, including resumes. The same release added `--system-prompt-snapshot off` to stop "reusing the conversation's recorded prompt", so the prompt is now stored with the conversation. If a resume reuses the recorded prompt, a changed append text on resume is silently ignored. That happens when orchestration is turned on after the chat started (adding `ORCHESTRATION_SYSTEM_PROMPT`) or when a Mainframe upgrade changes the AskUserQuestion text. The agent then runs on stale instructions and nothing errors. Confirm live whether a resume with different `--append-system-prompt` text gets the new text.
- Recommended regression test: if the live check confirms the problem, add `#[test] a_resume_whose_append_text_changed_renders_the_system_prompt_fresh` in `src/session_tests_spawn_part_2.rs`, next to `combines_the_askuserquestion_and_orchestration_prompts_into_one_flag`. It should pin `--system-prompt-snapshot off` in the resume argv when the append text differs from the one the chat was spawned with.
- Verify live: .claude/skills/claude-protocol-debugger/

### medium — Fixed policy-helper warnings not printing on headless (`-p`) runs (2.1.268)

- Checklist row: `CLAUDE-IO-01` — `src/events.rs::{is_informational, handle_stderr}`
- Why it threatens the row: `is_informational` drops only lines that start with `debugger`, `warning:`, `deprecationwarning`, `experimentalwarning`, `(node:`, or `Cloning into`. A stream-json session is headless, so on installs that use a managed-settings policy helper, these newly printed warnings reach `handle_stderr`. Any line that does not begin with `Warning:` shows up as a session error even though the session is fine. Only managed (enterprise) installs are affected. This is the second new headless stderr line, after the 2.1.233 `[claude-code:unrecognized_model]` line flagged on 2026-08-27, which `is_informational` still does not filter.
- Recommended regression test: capture a real policy-helper warning line from 2.1.268+ and extend `src/events_tests_stderr.rs::stderr_filters_informational_and_empty` with it verbatim. Assert that it classifies as informational, not just that handling succeeded.
- Verify live: .claude/skills/claude-protocol-debugger/

## Adoption opportunities

- `CLAUDE_CODE_MCP_STARTUP_WAIT_MS` (2.1.274), which bounds how long the first non-interactive turn waits for connecting MCP servers. It would go in `src/orchestration_args.rs::apply_orchestration_env` as one of the mitigations for the 2.1.274 risk above. Size: small.
- `--system-prompt-snapshot off` (2.1.267), which renders the system prompt fresh instead of reusing the recorded one. It would go in `src/session_spawn.rs::append_resume_args`, used only when the append text changed since spawn, as the fix for the 2.1.267 risk above. Size: small.
- `/output-style [name]` in headless sessions (2.1.269), which lists and switches output styles. It would be sent through `src/session_prompt.rs::send_command`, with a picker in the composer. Size: medium.
