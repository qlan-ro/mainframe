## Checklist drift found while verifying consumers

- `CLAUDE-EVT-06` is stale. It says `stream_event` is deliberately unhandled and `--include-partial-messages` is never passed. In fact `src/session_spawn.rs::build_args` passes the flag whenever `src/partial_stream.rs::supports_partial_messages` sees CLI ≥ 1.0.109, and `src/events.rs::handle_event` routes `stream_event` to `src/partial_stream.rs::handle_stream_event`. - `CLAUDE-FLAG-01` lists the modes `default|acceptEdits|bypassPermissions|plan`, but `build_args` also emits `auto` (`src/session_tests_spawn_part_1.rs::auto_mode_passes_permission_mode_auto`). Auto-mode entries are therefore relevant, and two are filed under no-action below.
- `CLAUDE-EVT-04` says context tokens come "only from the last parent-turn assistant `usage`". `src/assistant_event.rs::handle_assistant_event` stores `last_assistant_usage` *before* it returns early for a `parent_tool_use_id` event, so subagent usage can overwrite it. This is a pre-existing gap. It matters for the 2.1.287 forked-skill risk below.

## Compatibility risks

### high — Changed claude.ai connectors to negotiate MCP protocol version 2026-07-28 by default on installs that fetch no flags; `MCP_PROTOCOL_NEGOTIATION=legacy` opts out (2.1.295)

- Checklist row: CLAUDE-FLAG-04 — `src/orchestration_args.rs::orchestration_args` (argv); the version gate that would fail is outside this crate: `packages/core-rs/crates/mainframe-orchestration/src/protocol.rs::{SUPPORTED_PROTOCOL_VERSIONS, negotiate_version}` and `packages/core-rs/crates/mainframe-server/src/routes/mcp.rs` (admission check)
- Why it threatens the row: Mainframe's orchestration server is an HTTP MCP server injected with `--mcp-config`. Its supported list stops at `2025-11-25`, and the `/mcp` admission check answers HTTP 400 to any request whose `mcp-protocol-version` header is not in that list. Upstream is rolling MCP `2026-07-28` out by transport: stdio servers on every install in 2.1.292 ("Changed local (stdio) MCP server connections to negotiate protocol version 2026-07-28 by default on every install"), remote claude.ai connectors here, and only "on installs that fetch no flags". On installs that do fetch flags, a server-side flag picks the version, so HTTP config servers could already be on it. The 2.1.292 note that stdio servers which "ignore the newer protocol check" are only remembered after a slow connect suggests the new handshake is not a plain `initialize` version echo. If the CLI starts sending `2026-07-28` in that header to Mainframe's server, every request gets a 400. The CLI then treats the server as failed, and agents lose the `mcp__mainframe__*` tools without any error reaching the user. None of the entries in this range names `--mcp-config` HTTP servers yet, so this rates high on impact, not on confirmed exposure.
- Recommended regression test: the consumer is not in the adapter crate, so the test cannot be either. Extend `packages/core-rs/crates/mainframe-orchestration/src/protocol_tests.rs::version_negotiation_echoes_supported_and_falls_back_to_newest` with an `initialize` whose `protocolVersion` is `"2026-07-28"`, asserting the reply's `protocolVersion` is a version the server supports. Then add a route `#[tokio::test]` in `mainframe-server` that sends `mcp-protocol-version: 2026-07-28` and pins what the server returns, so the 400 becomes a deliberate choice instead of an accident. Before either, capture live what 2.1.295 sends to a `type: "http"` `--mcp-config` server: the header, the `initialize` version, and whether it falls back after a 400.

### medium — Fixed resume occasionally loading a transcript cut short when the same session rewrote the file during the load (2.1.288)

- Checklist row: CLAUDE-FILE-09 — `src/fork.rs::{copy_transcript, trim_trailing_partial_line}`
- Why it threatens the row: `copy_transcript`'s doc comment says outright "The transcript is append-only". `trim_trailing_partial_line` only handles a parent caught mid-append. This entry says the CLI can *rewrite* its own transcript while the session is live, which is exactly the failure the row's breakage column describes. If a whole-chat fork reads the file in the middle of a rewrite, the snapshot is a short but well-formed prefix. Nothing errors, and the fork resumes silently missing turns. A from-message fork is safer: `prefix_len_before_message` fails visibly when the cut uuid is absent. It is rated medium rather than high because it needs a race with a rewrite whose trigger the entry does not name.
- Recommended regression test: add `#[tokio::test] pin_rejects_a_snapshot_missing_the_last_known_message` in `src/fork_tests.rs`. Pin a parent JSONL that lacks the chat's last known vendor message uuid, and assert `pin_fork_point` returns an error instead of a shorter snapshot. This needs a small guard in `pin_fork_point` (pass the last known uuid in `ForkPinRequest`).

### medium — Fixed `--output-format stream-json` and the SDK not streaming the turns of a `context: fork` skill run by typing `/<skill>` as the prompt, as they do for the Skill tool's fork (2.1.287)

- Checklist row: CLAUDE-EVT-04 — `src/assistant_event.rs::handle_assistant_event` (sets `last_assistant_usage` before the `parent_tool_use_id` branch), `src/event_result.rs::handle_result_event`; also CLAUDE-IO-02 `src/session_prompt.rs::send_command`
- Why it threatens the row: Mainframe sends skills as typed slash commands (`send_command`'s `<command-name>` wrapper). For a `context: fork` skill, the CLI streamed nothing until the result. Now it streams the fork's turns. If they arrive with a `parent_tool_use_id`, they go to `on_subagent_child` under a tool_use id Mainframe never saw, so the blocks orphan. If they arrive without one, they render as main-thread messages. Either way, `handle_assistant_event` stores the fork's `usage` in `last_assistant_usage` before the subagent branch returns. The parent `result` then reports the fork's context size on the gauge, the regression the row names (#197). The same ordering already affects any subagent message that lands after the parent's last assistant message.
- Recommended regression test: add `#[test] subagent_assistant_usage_does_not_replace_the_parent_context_usage` in `src/events_tests_subagents.rs`. Feed a parent assistant event (usage A), then an assistant event with `parent_tool_use_id` (usage B), then a top-level result, and assert `on_result`'s `context_tokens` comes from A. The test fails against today's code. Then capture a typed `/<fork-skill>` run live to pin which `parent_tool_use_id` the streamed turns carry.
- Verify live: .claude/skills/claude-protocol-debugger/
