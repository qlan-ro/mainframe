## Compatibility risks

### medium — Changed auto mode with telemetry or feature flags off, including behind LLM gateways: calls the server can't check are asked about or denied, with no fallback to the built-in classifier; set `CLAUDE_CODE_AUTO_MODE_SERVER=0` to keep using it (Bedrock, Vertex and Foundry are unchanged) (2.1.319)

- Checklist row: CLAUDE-ENV-01 — `src/session_spawn.rs::build_spawn_command`, with the mode from `src/session_controls.rs::execution_mode_cli`
- Why it threatens the row: every `cliproxy/` chat runs behind a custom `ANTHROPIC_BASE_URL`, and Auto passes straight through as `--permission-mode auto`. The `auto_mode` capability is per adapter (`adapter/contract.rs:66`) and `PermissionSelect.tsx:69` filters on it, so Mainframe cannot hide Auto for a CLIProxy model today. If CLIProxyAPI does not pass the server check, these chats lose the fallback classifier. Each call the server can't check is then asked about or denied. A prompt reaches the user as `can_use_tool`, so an attended chat only gets noisier. A delegated or automated child waits on a permission prompt nobody is watching, and a denied call fails the step.
- The env var may not be the fix. The changelog says `=0` keeps the built-in classifier. The 2.1.319 binary says: "Its safety check runs on the server, and CLAUDE_CODE_AUTO_MODE_SERVER turns that check off here. Claude Code no longer has a check of its own to use instead." Strings can't show which case applies to a gateway. Both may be true on different paths. Do not set `=0` in the proxy branch until a live run settles it.
- Also check live: the binary adds "Auto mode can't check actions in this session and needs your choice", "choose: stay in auto mode, which can't check actions here, or leave it" and "Auto mode is unavailable: its safety check does not run for this session". If the choice is not a `can_use_tool` request, a stream-json session may never show it, and a refused `set_permission_mode` needs a visible error. Telemetry-off users on native chats may hit the same path, because the entry names that case too. Mainframe doesn't set it.
- Recommended regression test: after the live check, add `#[test] a_proxy_session_in_auto_mode_gets_the_verified_auto_mode_env` in `src/session_tests_spawn_part_1.rs`, next to `a_proxy_session_is_pointed_at_the_endpoint_and_stripped_of_the_real_api_key`. Pin the exact `CLAUDE_CODE_AUTO_MODE_SERVER` value, or its absence, that the run proves right. If the answer is to withdraw Auto for CLIProxy models, pin that with a test on the new per-model gate instead.
- Verify live: .claude/skills/claude-protocol-debugger/. Run a `cliproxy/` chat in Auto on 2.1.319, once unset and once with `=0`, and capture `can_use_tool` requests, denials and stderr.

### low — Fixed a config file left at the legacy name hiding your setup with no warning: Claude Code now says on stderr when a home holds two config files, and which is in use (2.1.319)

- Checklist row: CLAUDE-IO-01 — `src/events.rs::{is_informational, handle_stderr}`
- Why it threatens the row: the new text starts with `Two Claude Code config files exist: this run uses`. That matches no noise filter, so `handle_stderr` sends it to `sink.on_error`, and `handle_error` emits an error event for the chat. It should appear on each spawn, but only on a home holding both `~/.claude/.config.json` and `~/.claude.json`. The session keeps running. This machine has only `~/.claude.json`. Separately, `src/trust_store.rs` only knows `~/.claude.json`, so a run using the legacy file already reads identity and writes trust in the wrong place. The notice makes that gap visible.
- Recommended regression test: add `#[test] stderr_two_config_files_notice_is_not_a_chat_error` in `src/events_tests_stderr.rs`, pinning `Two Claude Code config files exist: this run uses /h/.claude/.config.json, not /h/.claude.json.` and asserting `sink.r().errors == 0`.
- Verify live: .claude/skills/claude-protocol-debugger/. Use a temporary `CLAUDE_CONFIG_DIR` holding both files, never the real home.
