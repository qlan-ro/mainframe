# Mainframe API Reference

The daemon's HTTP and WebSocket surface: every route it serves, the WebSocket
handshake and event protocol, and the response envelope both use.

This file is generated by hand from the Rust source, not Express. The daemon
used to be a Node/Express process (`packages/core/src/server/`); that package
is gone. The server now lives in `packages/core-rs/crates/mainframe-server`
(Axum), spawned by the `mainframe-daemon` binary in
`packages/core-rs/crates/mainframe-daemon`. When a route's behavior looks
wrong against this doc, read the route file it names — most carry a `PORT
STATUS` comment block at the bottom with the exact TS-to-Rust mapping notes.

Path parameters use axum's `{param}` syntax (the old Express docs wrote
`:param`; the wire format — `/api/chats/abc123` — is unchanged).

## Transport

| | |
|---|---|
| Base URL | `http://127.0.0.1:31415` |
| WebSocket | `ws://127.0.0.1:31415/` (same port, path `/`) |
| Port override | `DAEMON_PORT` env var; default `31415` (`mainframe-runtime::config::DEFAULT_PORT`) |
| Bind address | `127.0.0.1` only — the daemon never listens on a non-loopback interface. Remote access goes through the cloudflared tunnel (below), not a wider bind. |
| Body limit | 30 MB on every request (`tower_http::limit::RequestBodyLimitLayer`, matches the old `express.json({ limit: '30mb' })`) |
| Compression | Negotiated gzip/brotli on HTTP responses (Rust-side addition; the WS upgrade route is excluded so it never passes through the compressor) |
| CORS | Any `Origin` that resolves as a local/packaged-app origin is echoed back on `Access-Control-Allow-Origin`; `OPTIONS` gets a bare `204`; every response carries `X-Content-Type-Options: nosniff` |

The router is assembled in
`packages/core-rs/crates/mainframe-server/src/http.rs::build_app()`, which
merges one `Router` per file in `src/routes/` (41 files), nests the plugin
manager's router under `/api/plugins`, and mounts the two WebSocket upgrade
routes (`/` and `/lsp/{project_id}/{language}`) outside the compression layer.
Route method registrations total **150** across the 41 route files, plus
`GET /health` and the plugin manager's `GET /api/plugins` and
`GET /api/plugins/{id}` — **153** first-party HTTP endpoints, not counting
whatever routes a loaded plugin nests under its own id (dynamic; see
[Plugins](#plugins)).

## Authentication

Source: `packages/core-rs/crates/mainframe-server/src/middleware/auth.rs`,
`src/websocket.rs`.

- **No `AUTH_TOKEN_SECRET` set** (the common desktop-app case): the auth
  middleware is a no-op and every request is accepted, including from
  non-loopback peers. This is the default for a local daemon talking only to
  its own desktop shell.
- **`AUTH_TOKEN_SECRET` set** (remote/tunnel mode): a caller from a loopback
  address (`127.0.0.1`, `::1`) is still never rejected, but a valid `Bearer
  <device token>` on the request attaches a `TokenPayload` the route handlers
  can read. A caller from a non-loopback address must present a valid device
  token or gets `401 {"success":false,"error":"Unauthorized"}`; a rejection is
  logged with the path and a reason (`missing bearer` / `invalid token`) —
  never the token itself.
- **Always exempt, regardless of secret**: `GET /health`, and three of the
  pairing endpoints — `POST /api/auth/confirm`, `GET /api/auth/status`, `GET
  /api/auth/pair-status` (a client can't hold a device token before it has
  paired). `GET /api/auth/pair` is *not* exempt — pairing is initiated from an
  already-trusted device.
- **Webhook ingress is exempt by path**: any `POST
  /api/automation-webhooks/<hookId>` (exactly one non-empty path segment)
  skips the bearer check — external senders (GitHub, etc.) can't hold a device
  token, so the route HMAC-verifies the payload itself instead.
- **The auth layer covers 404s too**: the router's fallback 404 handler sits
  *behind* the auth middleware, so an unmatched path from a non-loopback
  caller without a token gets `401`, not `404` (mirrors Express's
  `app.use(authMiddleware)` running before the router's own 404).
- **WebSocket auth is separate from the HTTP layer.** The `/` and
  `/lsp/{project_id}/{language}` upgrade routes authenticate themselves via a
  `?token=<device token>` query parameter — never the `Authorization` header,
  since a browser/webview `WebSocket` constructor can't set custom headers on
  the upgrade request. Auth is required only when a secret is configured *and*
  the caller isn't loopback (`is_ws_auth_required`); an unauthenticated
  non-loopback upgrade gets a bare `401 Unauthorized` (no JSON body — the
  upgrade never reaches the envelope layer).

Pairing flow (`auth.rs`): `POST /api/auth/pair` mints a 6-character code
(5-minute TTL, 5 failed-attempt cap); the new device calls `POST
/api/auth/confirm` with that code plus a `clientDeviceId` (UUID v4) to receive
a device token; polling clients use `GET /api/auth/pair-status` to learn when
a code has been consumed. A 60-second sliding window caps failed confirms at
10 per IP (`429 Too many attempts, try again later`).

## Response Envelope

Source: `packages/core-rs/crates/mainframe-server/src/respond.rs`, mirrored
in TypeScript by `ApiResponse<T>` / `ApiResponseEmpty` in
`packages/types/src/api.ts` (`@qlan-ro/mainframe-types`).

```rust
pub fn ok<T: Serialize>(data: T) -> Response;   // 200 {"success":true,"data":<data>}
pub fn ok_empty() -> Response;                  // 200 {"success":true}
pub fn fail(status: StatusCode, error: impl Into<String>) -> Response; // {status} {"success":false,"error":"..."}
```

```json
// ok(data)
{ "success": true, "data": { "id": "p_123", "name": "mainframe" } }

// ok_empty()
{ "success": true }

// fail(404, "Project not found")
{ "success": false, "error": "Project not found" }
```

An unexpected error (a DB failure, an unmapped panic path) never leaks its
message to the client. Route handlers funnel those through
`async_err::internal_error(context, &err)`, which logs the real error via
`tracing` and always answers `500 {"success":false,"error":"Internal server
error"}` — the exact fixed string, byte for byte, regardless of what actually
failed.

## Envelope and Status-Code Deviations

Most routes are `ok` / `ok_empty` / `fail` exactly as above. A few are not —
this table is the fast way to find out which ones before you write a client
that assumes the standard shape.

| Route | Deviation |
|---|---|
| `GET /health` | Bare JSON (`{"status":"ok","version":...,"pid":...,"timestamp":...,"tunnelUrl":...}`), never the envelope. Always public. |
| `POST /api/projects` (path already registered) | `409 Conflict` body is `{"success":false,"error":"Project already registered","data":<existing Project>}` — a `data` field riding along with `success:false`, which `fail()` never otherwise produces. |
| `DELETE /api/tags/{name}` | `204 No Content` with an empty body — no `{success}` envelope at all. |
| `POST /api/automation-webhooks/{hookId}` | HMAC-verified webhook ingress. Status mapping instead of a uniform envelope: `200` (`ok_empty`) on both a fresh accept and a detected duplicate; `204` on a preset mismatch or a stale delivery; `400` invalid JSON / missing delivery id; `401` invalid signature; `404` unknown hook; `500` if starting the run itself fails (signal the sender to retry). |
| `GET /api/providers/{id}/quota` and `POST /api/providers/{id}/quota/refresh` | `ok_empty()` (`200 {"success":true}`, no `data`) means "no quota observation exists yet for this provider" — it is not an error. `refresh` answers `503` only when the quota service itself isn't wired into the daemon. |
| `POST /api/automations/{id}/runs` | `202 Accepted` on a manually started run (async work in flight), not `200`. |
| `POST /api/projects/{id}/git/*` (git_write.rs) | On a git failure, the raw git/CLI error message is put straight into the `500` envelope's `error` field — the one deliberate exception to the "never leak the real error" rule, because the git error text is itself the useful diagnostic. |
| WebSocket upgrade rejection | Plain `401 Unauthorized` with a bare text body, not JSON — the upgrade never reaches the HTTP envelope layer. |

## WebSocket Protocol

Source: `packages/core-rs/crates/mainframe-server/src/websocket.rs`,
`ws_schemas.rs`; wire types in `packages/types/src/events.ts`
(`ClientEvent`, `DaemonEvent`).

### Connecting

Open a WebSocket to `ws://127.0.0.1:31415/`. If auth is required (see
[Authentication](#authentication)), append `?token=<device token>`. On
success the daemon sends, as the first frame:

```json
{ "type": "connection.ready", "clientId": "ab12cd34" }
```

immediately followed by one `adapter.models.updated` event per adapter whose
model catalog has already been probed (so a fresh connection's model list is
correct without waiting for the next probe cycle).

### Client → Server Events

Every frame is JSON with a `type` discriminant. An unparseable frame (bad
JSON, or JSON that doesn't match one of these six shapes) gets back `{"type":
"error", "error": "Invalid JSON"}` or `{"type": "error", "error": "Invalid
message: <reason>"}` — the connection stays open.

| `type` | Fields | Validation |
|---|---|---|
| `subscribe` | `chatId` | non-empty |
| `unsubscribe` | `chatId` | non-empty |
| `subscribe:file` | `path`, `projectId?`, `chatId?` | `path` non-empty; a relative `path` requires `projectId` |
| `unsubscribe:file` | `path`, `projectId?`, `chatId?` | `path` non-empty |
| `message.send` | `chatId`, `content`, `attachmentIds?`, `metadata?` | `chatId` non-empty; `content` or a non-empty `attachmentIds` required; `metadata.command.name` must match `^[a-zA-Z0-9_-]+$` |
| `permission.respond` | `chatId`, `response: ControlResponse` | `chatId` non-empty |

`subscribe` registers the connection for a chat's events and immediately
replies with three frames, in order: `message.queued.snapshot` (any queued
messages for that chat), `worktree.offer.snapshot` (any pending worktree
offers — sent even when empty, since this snapshot is the client's only
re-seed path), then `subscribe:ack`.

`message.send` registers the sending connection as a subscriber of `chatId`
*before* dispatching, so events emitted in the gap between send and the
client's own `subscribe` frame are never dropped.

### Server → Client Events

Every event is JSON with a `type` discriminant (dot-separated, a few legacy
colon-separated exceptions noted below) and, where relevant, a `chatId`.
Delivery is scoped: an event carrying a `chatId` reaches only connections
subscribed to that chat, *except* three connection-global types that reach
every connection regardless of subscription: `chat.notification`,
`permission.requested`, `automation.notification`. An event with no `chatId`
at all (adapter/provider/automation-level events) also reaches everyone.

### ACP Chat Facade (`/acp/{profile}`)

Source: `packages/core-rs/crates/mainframe-acp` (pure dispatch, no socket
code) and `packages/core-rs/crates/mainframe-server/src/acp_ws.rs` (the axum
upgrade shell); vendored wire types in
`packages/core-rs/crates/mainframe-types/src/acp/` and
`packages/types/src/acp/`.

The daemon exposes a second, additive-only chat surface: an [ACP
v2](https://agentclientprotocol.com) server facade, frozen against snapshot
`d0370de50e16` (`docs/research/ACP-EVALUATION.md`), plus a `_mainframe.dev`
extension namespace for what ACP has no construct for. It replaces the legacy
dialect's whole-message resends, `task_group` double-encoding, and four
separate reconnect re-seed paths with versioned, delta-streamed, explicitly
framed turns — see `docs/specs/2026-08-28-todo-350-wire-protocol-payload-grammar.md`
for the full grammar rationale.

**Status: live on the daemon.** `/acp/{profile}` serves the full facade:
`session/prompt`/`session/cancel` run against the live `ChatManager`
(`mainframe-server/src/acp_ws/ports.rs`), `session/resume` replays from the
cursor and seeds the connection's diff state, gates raise/resolve through
the chat-surface observer (`FacadeHub`, attached at boot), and attached
connections stream `session/update` with server-side coalescing
(`FACADE_THROTTLE_INTERVAL_MS`). A connection observes a session once it has
prompted or resumed it; one connection multiplexes any number of sessions.
The desktop UI still speaks the legacy dialect — switching its controller to
`acp-client.ts` is the remaining cutover work, tracked separately.

**Connecting.** `GET /acp/{profile}` (upgrade), where `profile` names a
registered adapter (`claude`, `codex`, `mock-cli`, …) — unregistered profiles
get `404`, matching the auth-then-existence check order the legacy route
uses. `?token=` works exactly as it does on `/`.

**Handshake.** The client sends `initialize` with `protocolVersion: 2`
(`PINNED_PROTOCOL_VERSION`); a mismatched version gets a structured
`-32001` error (`data.supported: [2]`) and the connection stays open. The
response's `_meta["_mainframe.dev"]` carries `MainframeCapabilities`
(`richPermissionAnswers`, `queuedPrompts`, `retryMarkers`,
`heartbeatIntervalMs`) — a generic ACP client that ignores this namespace
gets a degraded but coherent experience (plain option-only gates, no
queued-turn metadata).

**Methods and notifications (shipped grammar):**

| Method / notification | Direction | Purpose |
|---|---|---|
| `initialize` | client → daemon | Version negotiation + capability advertisement. |
| `session/prompt` | client → daemon | Send a turn; response is acceptance (immediate or queued via `_meta`), never turn completion — no `queue.*` frame family. |
| `session/cancel` | client → daemon (notification) | End the turn with a cancelled stop reason; cancels open gates. |
| `session/resume` | client → daemon | Replay from an opaque `replayFrom` cursor (`{type:"start"}` or `{type:"item",itemId}`); unknown/pre-compaction cursor falls back to a full replay carrying `_meta["_mainframe.dev"].fullReplay: true`. |
| `session/request_permission` | daemon → client | Mid-turn blocking gate with an adapter-supplied ordered option list (`allow-once`/`allow-always`/`reject-once`); a plain `{outcome:"selected", optionId}` answer is always valid, a rich `_meta["_mainframe.dev"].controlResponse` answer carries today's `ControlResponse` semantics (input mutation, execution mode, clear-context) and is validated against the request it claims to resolve before being trusted. |
| `session/update` | daemon → client (notification) | Item chunks/upserts/patches — `AgentMessage(Chunk)`, `UserMessage(Chunk)`, `AgentThought(Chunk)`, `ToolCallUpdate`, `ToolCallContentChunk`, `StateUpdate`, `UsageUpdate`. Diffed per session (`SessionState`) so no frame after an item's first repeats its full accumulated content. |
| `_mainframe.dev/heartbeat` | daemon → client (notification) | Periodic `{sequence}` at `heartbeatIntervalMs`; a sequence gap larger than one is the client's signal to call `session/resume` instead of heuristically refetching (the sync contract this protocol formalizes). |
| `_mainframe.dev/gate_resolved` | daemon → client (notification) | `{sessionId, requestId}` pushed to every connection still holding a delivered gate when it resolves elsewhere (another facade client, the legacy surface, or the CLI cancelling it); `requestId` is the gate's `session/request_permission` JSON-RPC id (`gate-{id}`). The answering connection gets its resolution through its own response exchange, not this frame. |

**Subagents.** Flatten to ordinary tool-call items carrying
`_meta["_mainframe.dev"].parentToolCallId` — there is no `task_group` frame
on the facade (`mainframe-acp::encoder`).

**Edit/Write fidelity.** A tool result carrying structured hunks adds a
`diff` entry to the tool call's `content` (spec Decision 15): `changes`
names the affected absolute path and operation, `patch` carries git-patch
text a generic ACP client can render, and the diff's own
`_meta["_mainframe.dev"]` carries the `structuredPatch`/`originalFile`/
`modifiedFile` payload the desktop Edit/Write cards consume.

**Truncated tool results.** When the daemon truncates an oversized tool
output for display, the result's text content block carries
`_meta["_mainframe.dev"]: {truncated: true, fullBytes}` (spec Decision 20) —
the same pair the legacy dialect's `ToolCallResult` carries inline — so a
client can offer the on-demand full-output fetch
(`GET /api/chats/{chatId}/tool-result/{toolUseId}`). Generic ACP clients
ignore the marker and render the truncated preview text.

**Multi-client + cross-surface gates.** A gate raised on a chat broadcasts
to every facade connection attached to it, under the shared correlation id
`gate-{requestId}`; only the first answer applies
(`mainframe-acp::gate_registry`). Answering a gate on the legacy `/` route
raises `GateResolved` on the same chat-surface observer the facade hub
implements (`mainframe-chat::permission_handler`), so a legacy-surface
answer drops the facade's pending delivery and a late facade answer is
rejected as resolved — one observer, no separate synchronization. A
still-open gate is redelivered by `session/resume` under the same id.
Resolution is pushed: every connection still holding the delivered gate
receives `_mainframe.dev/gate_resolved` the moment it resolves (criterion
8), so a second client's pending gate clears immediately; resume redelivery
remains the fallback for a client that was disconnected at that moment.

**Migration window.** The legacy dialect above stays byte-frozen for the
duration; desktop cuts over first, `packages/mobile` follows in its own PR
against this same pinned `protocolVersion: 2`. Both dialects run
side by side until both clients have migrated, at which point the legacy
chat events are removed (tracked as a follow-up todo, not part of #350).

### LSP WebSocket

`GET /lsp/{project_id}/{language}` (upgrade) — a separate, self-authenticating
upgrade route that bridges the socket directly to a spawned language-server
child process (raw LSP JSON-RPC frames, not `ClientEvent`/`DaemonEvent`). A
reconnect replays the cached `initialize` response from the first connection.
**Known gap:** if a client reconnects after the *first* bridge already
consumed the child process's stdout/stderr, the reattach can't re-proxy those
streams (`start_reattach_bridge` logs a warning) — a language server survives
across the daemon's own gaps, not across arbitrary client disconnect/reconnect
cycles.

## What's Not Verified or Not Mounted

- **Per-plugin sub-routes** (`/api/plugins/{id}/*`) are defined by whatever
  plugin is loaded, not by `mainframe-server`. This doc does not enumerate
  them; read the plugin's own router (e.g. the built-in `todos` plugin) for
  its routes.
- **`launch.json` configuration shape** is read and validated on the daemon
  side (`parse_launch_config`) but this doc does not reproduce its full
  schema — see `packages/core-rs/crates/mainframe-runtime` for the parser if
  you need the exact fields.
- **Automation definition/step-config bodies** (`POST`/`PUT
  /api/automations*`) accept the full Automations v2 step-graph shape, which
  is large enough to warrant its own reference; this doc gives the route
  surface, not the step schema. See `packages/types/src/automation.ts` and
  `automation-domain/`.
- **`GET /api/settings/general` / `/providers` response bodies** are
  assembled dynamically (a `serde_json::Map` built field-by-field from
  stored settings rows, not a single named struct), so this doc describes
  their shape in prose rather than a type reference.
