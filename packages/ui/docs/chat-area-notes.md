# Chat area notes

Read this when changing one of the areas below. The ownership rules are in the "assistant-ui boundary" section of [`../CLAUDE.md`](../CLAUDE.md); these notes record how each area is built today and the decisions behind it.

## assistant-ui areas

- **Composer → MATCH (~90% native, restyle).** `ComposerPrimitive` Root/Input/Send/Cancel (`asChild`→our icon buttons, swap on `thread.isRunning` via `AuiIf`)/AddAttachment/AttachmentDropzone/Attachments/Quote. **Keep `QueuedUserTurn` (daemon-backed); the native `Queue` is a different local model — do NOT use it.** Build the config toolbar (model+effort+features in one menu, plan, permission, worktree) as **stateless** shadcn children that **PATCH the daemon directly** — `/api/chats/:id/config` (model/plan/permission) + `/tuning` (effort/features), Zod-validated daemon-side — NOT `composer.setRunConfig` (that targets the AI-SDK transport, inert under our external-store runtime). **Config is server-authoritative with NO optimistic edits** (judo-B): the controller owns it (seeds from REST on load, mirrors every `chat.updated` into `state.chatConfig`); `useComposerTuning` reads `extras.state.chatConfig` live and a control just fires the PATCH — the daemon's broadcast updates the toolbar. This matches the desktop client and avoids the optimistic-vs-broadcast flicker. **`/`-skills + `@`-file pickers → DONE: native `Unstable_TriggerPopover` (reversal of the earlier shadcn-`Command` call).** Both triggers live on one `Unstable_TriggerPopoverRoot` wrapping the composer (`features/chat/composer/triggers/`): `/` (daemon slash commands, then skills — sync adapter over a per-chat `SkillsProvider`; commands lead so a handful of them stay visible above hundreds of skills, and the send path re-matches the invocation from `command-registry` to attach `metadata.command`) and `@` (files, an async-over-sync adapter — debounced `searchFiles` into a cache the sync adapter reads). Insertion uses a **custom literal directive formatter** (`serialize → "<prefix><id> "`, `parse → all-text`) so the sent message carries plain `/skill` / `@path` text the CLI parses — NOT directive chips. `@` is **insert-text-only** (no `POST /mentions`). Adapter types are local structural copies (`@assistant-ui/core` isn't resolvable; item/formatter types come from `@assistant-ui/react`). ⚠️ `Unstable_` API — exact-pinned; coupling kept in the small adapters. Custom thumbnail (native `Thumb` is @alpha/extension-only). **Never `useComposer()`** (getSnapshot loop) — `useAuiState` + `useAui().composer`. **New-thread flow is draft-aware (D3 preserved):** the picker is skipped when a project pill is active; the live adapter/model/permission/plan/effort/feature selectors are usable on the `__LOCALID_*` draft before the first send; the chat is still created on the **first send only** (no empty sessions). **Known follow-up: provider-tuning-defaults are not yet fetched** — `ModelMenuRow`/`use-composer-tuning` pass `undefined` for the provider-defaults arg, so controls resolve model-effort/feature constraints without provider inheritance until a settings/provider-defaults fetch lands (tracked in the tracker backlog).
- **Quote / select-to-quote → MATCH (use native).** `SelectionToolbar` (floating quote button on text selection — **replaces our `QuoteOnSelectionButton`**), `MessagePrimitive.Quote` + `QuoteBlock` (inline quote in the user message), `ComposerPrimitive.Quote/QuoteText/QuoteDismiss` + `ComposerQuotePreview` (composer pill). Install the shadcn `quote` component and restyle; don't re-implement selection/quote handling.
- **Sessions / thread-list → HYBRID (decided).** One global `useRemoteThreadListRuntime` (all sessions; domain data in thread `custom`: projectId/tags/prState/worktree/status/pinned) + native `ThreadListItemPrimitive` rows (rename/archive/delete/select/active) rendered inside **our** grouped/filtered/pinned sidebar layout via `ThreadListItemRuntimeProvider`/`ThreadListItemByIndexProvider`. NOT the flat default `ThreadListPrimitive.Items`; NOT per-project runtimes. **BUILT (step 11).** Verdicts: D10 — native Archive kept; deleteWorktree choice resolved inside adapter.archive via the archive-confirm bridge (ArchiveWorktreeDialog mounted ONCE at the App root, not in SessionSidebar) before calling archiveChat; throwing on 'cancel' rolls back aui's optimistic archive. D11 — Pin + right-click context menu in scope; shadcn ContextMenu wraps ThreadListItemPrimitive.Root with Pin/Unpin/Rename/Archive/Copy Session ID; the Tags action opens TagPopover via the use-tag-popover-target store + a single TagPopoverHost at root. D12 — filter pill is view-only (no auto-activate); no direct-create shortcuts on New-click; blank/last-thread fallback when the active chat is archived; cross-project activate clears the project filter (setFilterProjectId(null)); granular responsive row hiding shipped. Keep-warm: controllers stay in the registry across switches; the WS subscription is gated to the active thread only (ChatWsSubscription helper; controller never subscribes a __LOCALID_* chat). New uses new-thread-coordinator.createForLocal for the __LOCALID_* → remoteId handoff on first send (id stays __LOCALID_* for life — controller.setRemoteId stamps remoteId, no id-flip). **Grouping = TIME by default, with an opt-in Project mode** (2026-07 rebuild): Pinned/Today/Yesterday/Earlier via `arrangeSessions` stays the default; the Sort By menu now has a 4th option ("Project") that groups sessions into one section per project (project-list order, pinned still first) via the same `arrangeSessions` — additive, doesn't change the other 3 modes. Project narrowing is primarily the **project switcher list** (`ProjectFilterPillBar.tsx` — despite the name, a vertical one-click list now, not a pill-cloud: "All projects" row + one row per project with a colored initial avatar + attention badge, collapsible past 5 via "Show N more"). **One-line session rows (redesign L1–L4):** project letter, title, then one trailing value — a spinner, "needs you" or the time (`view-model/session-status.ts`); everything else (project, worktree/branch, PRs, tags, provider, lineage, missing-checkout warning) lives in the `SessionMetaCard` shown on hover or keyboard focus, whose links Tab reaches from the row (`use-session-meta-card.ts`). **Design-conformance pass done** (rendered-and-diffed vs `02-chrome.jsx` SessionRowDense/Sidebar): translucent panel (`bg-background/85` + `backdrop-blur-xl` since the 2026-08-07 token retirement), **collapsible wrapping tags bar (+N more — no horizontal scroll)**, thin warm auto-hide scrollbar (`mf-thin-scrollbar`). **Boot auto-opens the most-recent session** (parity with desktop) so the app never lands on an empty thread. **Window chrome (redesign 2026-10-04, title bar segmented 2026-11-24):** the shell is a COLUMN over a ROW — a 48px `TitleBar` on `bg-sidebar` spans the window (the one `data-drag-region`; native traffic lights at `trafficLightPosition` y=22, patched to 26 for SDK 26 dev builds; 80px reserve). It is cut into segments whose separators stand on the column edges below — lights + usage capsule │ `SessionTabs` │ workspace tabs + `+` + Files (`TitleBarWorkspace`, only while the workspace shows) │ Search + the Chat / Workspace toggles. **Edges are measured, never computed:** a column reports its left edge through `useColumnEdge` (`layout/column-edges.ts`) and draws its hairline on the pixel just left of it. Under it a 56px `NavRail` (its own column, hairline on its right; Chats · Tasks · Automations; update · appearance · Settings) and ONE `ContentCard` (square, hairline on top, `bg-background`) holding the `AppSidebar` view host and the chat. The chat column holds ONE conversation, under its own title row (`ChatColumnHeader`); session tabs live in the title bar. Split chats are retired (W9, 2026-11-25): every secondary chat — fork, side chat, delegated task, sub-agent, another session — is a workspace tab (`features/workspace-chat/`). The session panel DOCKS (300px flex sibling at ≥ 1044px column, overlay otherwise; `panel-mode.ts`); there are no floating panels and no rail. The sidebar is 260px (`SIDEBAR_WIDTH`), persisted in `ui-prefs` v8 with `sidebarView`. **DEFERRED sidebar chrome (separate leaves, NOT built):** the remaining **Run surface CONTENT** (the Files editor and the Run **terminal** are DONE 2026-06-11/06-13; the **sandbox preview** tab — embedded Tauri webview — is the last Run-content leaf), the warm **radial-gradient window background** behind the floating panels (today flat `bg-background`), the ghosted/dashed "Add project" pill (needs the add-project flow — `features/sessions/sidebar/ProjectFilterPillBar.tsx`), and the SessionSidebar group-header "more" popover (`SessionSidebar.tsx` — a presentational placeholder button, no menu wired). These complete full-sidebar artboard parity but are larger surfaces beyond the sessions list. **The bottom Context/Skills/Agents tabbed panel is no longer deferred — it is ABSORBED** (2026-08-06, right-sidebar revamp): its content moved into the right-hand session panel (`features/session-panel/`), and `features/context-panel/` is deleted. Two capability decisions came with it. **D14:** in-session file mentions survive as a "Session" sub-group under Context — `derive-session-items.ts` and `ContextFileItem.tsx` moved into the panel rather than dying. **D15: agents are dropped from the product surface entirely** — no list renders `AgentConfig` after this PR, `AgentsList` is gone, and `useSidebarSkills` no longer fetches them. `lib/api/agents.ts` and its daemon route stay: the Setup Advisor still uses the endpoint. That is a deliberate, visible capability loss, not an oversight.

**Framing (don't repeat the over-conservative mistake):** the native *runtime-integration hooks* — `ModelContext.register`, `useThreadTokenUsage`, `useAssistantInstructions` — are **INERT under our external-store runtime** (they target the AI-SDK transport). But the native *presentational components* work fine. So the pattern is almost always **native component + our CLI/daemon data + our config-write path**, NOT "keep ours." e.g. `ModelSelector.Root` (composable, not the default export) fed our models; `ContextDisplay.Bar` with its external `usage` prop fed our CLI usage; `MessageTiming` fed `metadata.timing`; native `Image`/`File` parts fed `convert-message`; the `SyntaxHighlighter`/`CodeHeader` slots fed our shiki engine. Per-feature verdicts (6 adopt-native / 9 native-shell+our-data / 9 genuine keep-ours) were tracked in a migration-inventory doc that never made it into the tree — the summary above is what survives.

## Mainframe areas that still use assistant-ui pieces

- **Turns and tool rows → Mainframe's.** A turn spans several messages (a compaction, a loaded skill or a delivered task result can fall between its parts, and the provider can start a turn with no user message), so `view-model/turn` groups the messages and `messages/turn/TurnSlice.tsx` draws one message's share of its turn. The slice iterates the parts itself, and `ToolRow` dispatches on `toolKind`; `MessagePrimitive.GroupedParts`, `tools.by_name` and assistant-ui's tool cards are not used. The row primitives still come from assistant-ui (`ThreadPrimitive.MessageByIndex`, `MessagePrimitive.Root`, `ActionBarPrimitive`, `ReadonlyThreadProvider` for nested transcripts), and text renders through `TextMessagePartProvider` + `MarkdownTextPrimitive`. Row presentation is moving onto shadcn Trace and tool output onto Code Block.
- **Permissions / ask / plan → DONE: inline gate cards, hybrid (native inline parts + our `extras` reply).** Correction to the earlier note: assistant-ui's native tool **`approval`** gate (the tool-call `approval` field + the `respondToApproval` prop, backed by the external-store adapter `onRespondToToolApproval`) **IS usable** under our `useExternalStoreRuntime` — it's data-driven, not transport-coupled. Only the separate `hitlTool()`/`interrupt:{type:'human'}`/`resume()` path is inert (needs a "use generative" compiler). We bypass the native `approval` plumbing **by choice** because our gate data is out-of-band (`control_request` → `extras.permissions`), not in the message stream. Shipped: 3 prop-driven cards (`PermissionGate`/`AskUserQuestionGate`/`PlanGate`) under `features/chat/gates/`, dispatched by `ControlRequest.toolName` from a single `ChatGateMount` mounted in the thread's sticky footer above the composer (`ChatThreadViewport.tsx`; a plain div, not `ThreadPrimitive.ViewportFooter`, whose height 0.15.38 counts as "at bottom" for the scroll-to-bottom button), inside a height-capped, internally-scrolling slot (`chat-thread-gate-slot`) so a pending gate never scrolls out of reach (#336), reading the queue-front via `useChatPermissionFront` (sorts `extras.permissions` by `askedAt`) and replying through `replyToPermission`. Permission cards dismiss on answer; AskUserQuestion/Plan persist via the existing tool-result display cards. Queue-front-only (one gate at a time); the gate renders the daemon's adapter-supplied option list **verbatim** (`chat-permission-option-{optionId}`, styled by `kind`, never by id/label — spec decision 12; unknown kinds render neutrally and answer as deny, decision 25); **don't invent** risk levels/scopes/per-arg toggles. **Reply seam (judo-C):** `replyToPermission`/`ReplyFn` take the `ControlResponse` (it carries its own `requestId`, so there is no separate id to desync) plus the clicked option's `optionId`; Plan/Ask answers omit the option and the session plane synthesizes one. **Lost answers self-heal via resume:** answering optimistically drops the gate; if the answer dies with the socket, the facade reconnect's `session/resume` redelivers the still-open gate under the same correlation id (the legacy 3s re-read + `GET /pending-permission` restore path is retired). Plan: `docs/plans/2026-06-05-interactive-chat-gate-cards.md`; memory: `aui-approval-gate-external-store`.
- **Markdown / reasoning / parts** → assistant-ui part components; restyle. **Reasoning: DECIDED — show the native `Reasoning` block, collapsed by default** (drop the dead `ThinkingPart`).
